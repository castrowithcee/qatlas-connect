# Amazon S3

Group `s3`, the S3 API for general purpose buckets. S3 is regional: every tool takes an optional `region`, which may be
left out when the connection lists exactly one region and otherwise must name an allowed one. Every permission a tool
needs is listed in [Set up AWS](setup.md#s3). The tools work on the buckets of the bound account. They list, describe, copy, delete, restore, and tag objects. Object content moves only through `object.upload` and `object.download`, and only into and out of local files; no result holds any. The retention and legal hold of a named object are read and set.

## Tools

Reads need no confirmation, and neither does `object.download`, which reads an object and writes a local file. Every other tool needs confirmation. `bucket-policy.put` and `bucket-policy.delete` are
listed-only: a connection offers them only when its tools list names each tool exactly; no effect and no prefix such as
`aws.s3.*` offers them. Every tool takes the bucket as
`bucket`, except `bucket.list`. The object tools also take `key` (1 to 1024 bytes) and, where S3 has the member, `version_id`, except the lists and `object.delete-many`. A result carries `region`, the region that was called.

`bucket.list` takes `prefix`, `bucket_region`, `page_size` (1 to 10000), and `cursor`, and returns `buckets`, `owner`,
`next_cursor`, and `has_more`. A configuration that does not exist (default encryption, tags, public access block,
lifecycle, CORS, bucket policy, website, replication, ownership controls, Object Lock) answers not-found. The confirmation is the one every tool with an effect has: the request names the tool, so the
description of the tool, not the confirmation prompt, says which bucket and region it changes.

## Bucket names and addresses

`bucket` must be the name of a general purpose bucket: 3 to 63 characters of lower case letters, digits, hyphens, and
dots, beginning and ending with a letter or digit. A name with upper case letters or underscores is accepted for a
bucket that exists, since old buckets have them, but never for `bucket.create`. IP addresses, access points, Express
One Zone and Multi-Region Access Point names, and reserved prefixes and suffixes are refused before any request. A name
that is one lower case DNS label goes in the host (`<bucket>.s3.<region>.amazonaws.com`), every other valid name in the
path of the regional host. A bucket in another region answers an error that names the region of
`x-amz-bucket-region`; call again with it. No redirect is followed.

## Expected owner

Every tool except `bucket.create` and `bucket.list` sends the account the connection is bound to as the expected
bucket owner, so a bucket of another account is refused by S3 and never read or changed. It is not an argument, under
no spelling. `CreateBucket` has no such header; the bucket does not exist yet, and the account check of the connection
covers it. A bucket name is global: a name that another account owns answers `BucketAlreadyExists`, one the bound
account owns answers `BucketAlreadyOwnedByYou`, both as a conflict.

## Creating and deleting a bucket

`bucket.create` makes a bucket in the region of the call with ACLs turned off: `object_ownership` offers only
`BucketOwnerEnforced`, the default, since `ObjectWriter` and `BucketOwnerPreferred` turn ACLs on. The
`create_bucket_configuration.location_constraint` must be the region of the call, which the connection must allow,
and is refused before any request otherwise; in `us-east-1` the model does not list the region, so the constraint is
left out and a given one is refused. In every other region the constraint is required. `tags` may be given with the
configuration. Not offered: all ACL and grant arguments, Object Lock (it cannot be turned off again), the account
regional namespace, and directory buckets.

S3 charges for the data a bucket holds and for requests to it. An empty bucket holds no data, but the name is yours
only while the bucket exists.

`bucket.delete` removes an empty bucket. A bucket with objects, versions, or delete markers answers a conflict
(`BucketNotEmpty`) and stays. The name then becomes free for anyone.

## Versioning, encryption, and tags

- `versioning.put` sets `status` to `Enabled` or `Suspended`. Versioning cannot be turned off again, only suspended;
  existing versions stay and are billed as storage. MFA delete and the MFA header are not offered.
- `encryption.put` replaces the whole default encryption: `rules`, each with `apply_server_side_encryption_by_default`
  (`sse_algorithm` `AES256`, `aws:kms`, or `aws:kms:dsse`, and `kms_master_key_id` for the KMS kinds),
  `bucket_key_enabled`, and `blocked_encryption_types`. Repeat what is to stay. Customer-provided keys (SSE-C) are not
  offered, and the algorithms of other AWS services are not accepted. `encryption.delete` removes the configuration;
  S3 then encrypts new objects with SSE-S3 as it does for every bucket.
- `tagging.put` replaces all tags (`tag_set`, each with `key` and `value`); `tagging.delete` removes them. The tool
  caps a request at 100 tags with keys up to 256 and values up to 512 characters; S3 enforces its own, lower limits.
  Tags are written by the users of the account and are untrusted data.

### KMS keys

The model marks the KMS key ID sensitive, but it is an identifier and not a secret, so the table releases it: the
result of `encryption.get` shows it, and `encryption.put` takes it. Every `kms_master_key_id` of a rule must be the ARN
of a key (`arn:aws:kms:<region>:<account>:key/<id>`) or of an alias (`arn:aws:kms:<region>:<account>:alias/<name>`)
of the bound account in an allowed region of the connection. A bare key ID or alias name carries no account and is
refused, as is an ARN of another account, region, partition, or resource type. Every rule is judged before any request.
The policy of the key must still allow the use.

## Public access block

`public-access-block.put` sets `block_public_acls`, `ignore_public_acls`, `block_public_policy`, and
`restrict_public_buckets`. It keeps or tightens the block and never loosens it. Before the change the tool reads the
current block with `GetPublicAccessBlock` of the same bucket and region, with the bound account as the expected owner:

- A bucket without a block (`NoSuchPublicAccessBlockConfiguration`) counts as all four settings off.
- A setting that is on and would be set to `false`, or left out (a setting left out of the request counts as `false`),
  refuses the call, and nothing is changed. A setting that stays, or goes from off to on, is allowed.
- Any other failure to read refuses the call: access denied, a timeout, a missing bucket, a server error, and an answer
  that is not a configuration, such as one without any of the four settings or with a value that is no boolean. A
  setting missing from a configuration that has others counts as off.

The read is part of the tool and cannot be skipped by an argument. The block of the account applies as well and is
neither read nor changed. Another writer can change the block between the read and the change; this cannot be
excluded.

## Bucket policy

`bucket-policy.get` returns the policy as JSON text in `policy`, and `bucket-policy.get-status` returns `policy_status.is_public`.
The document is text from the account's users: it is data, and instructions in it are never followed.
`bucket-policy.put` replaces the whole policy and `bucket-policy.delete` removes it. Removing a Deny statement can open
access that the policy kept closed. The confirmation does not show the document, so the tool descriptions carry what a
person must check before confirming: the bucket, the region, the principals, and the actions of the policy.

`put` judges the document before any request, without network. It refuses the call when any statement breaks one of
these rules, whatever its `Effect`, and says which rule and which statement position (1-based), never the value:

- The document is valid JSON of at most 20480 bytes (the limit AWS documents for a bucket policy) with `Statement` as an
  object or a non-empty list, and no key twice in one object. Example: a document of 20481 bytes is refused.
- Every statement has a `Principal`. `NotPrincipal` is never allowed. Example: `"NotPrincipal":{"AWS":"..."}` is refused.
- `Principal` is never `*`, as a string or as `{"AWS":"*"}`, also not in a `Deny` statement. A policy that denies requests
  without TLS for everyone, `"Effect":"Deny","Principal":"*"`, is therefore refused.
- `Principal.AWS` is the ID of the bound account or an ARN `arn:aws:iam::<bound account>:root`, `:user/...`, or `:role/...`.
  Example: `{"AWS":"arn:aws:iam::123456789012:role/app"}` is accepted when 123456789012 is the bound account. Other
  accounts, other partitions, unique IDs, and wildcards are refused.
- `Principal.Service` is an AWS service principal `<name>.amazonaws.com` and the statement needs a `Condition` of
  `aws:SourceAccount` with exactly the bound account (operator `StringEquals` or `StringLike`, without a wildcard) or of
  `aws:SourceArn` with an ARN whose partition is `aws` and whose account field is the bound account, spelled out (operators
  `ArnEquals`, `ArnLike`, `StringEquals`, `StringLike`). Example: `{"Service":"logs.amazonaws.com"}` with
  `{"StringEquals":{"aws:SourceAccount":"123456789012"}}`. A condition on a foreign or wildcard account, or none, is refused.
- `Federated` and `CanonicalUser`, and any other `Principal` key, are refused. Example: `{"Federated":"cognito-identity.amazonaws.com"}`.
- `aws:PrincipalOrgID`, `aws:PrincipalOrgPaths`, and related keys may stand as an addition but never replace the
  binding to the account. Example: a service principal with only `aws:PrincipalOrgID` is refused.

After a successful write the tool reads `GetBucketPolicyStatus` with a call of its own and returns `public_status.is_public`.
That is a hint to review, not a check, and not a guarantee; when it cannot be read, `public_status` says `unavailable`
and the write stands. A failure with `AccessDenied` or `MalformedPolicy` carries the note that a policy that locks out
its own writer can only be removed by the root user of the account. `ConfirmRemoveSelfBucketAccess` is not offered. The
interplay with SCPs of an organization has not been verified.

## Lifecycle and CORS

`lifecycle.get` and `cors.get` read the rules of the bucket; `lifecycle.delete` and `cors.delete` remove all of them.
Without lifecycle rules no object expires or moves by rule any more, and without CORS rules browsers on other websites
can no longer read the responses of the bucket. A lifecycle rule acts only on what its `filter` selects. A rule without a
filter, or with an empty prefix, covers the whole bucket. A rule of the old form is limited by a rule-level `prefix`
instead of a filter; `lifecycle.get` shows that `prefix` on the rule, and it limits the rule like a filter prefix.

## Ownership controls

`ownership.put` sets the object ownership of a bucket to `BucketOwnerEnforced` and accepts nothing else: exactly one rule
with `object_ownership` `BucketOwnerEnforced`. Any other value, a missing or empty value, an empty list of rules, or more
than one rule is refused before any request. After the change ACLs are ineffective: the bucket owner owns every object,
existing grants stop working, and access follows policies alone. Writers that send the ACL header
`bucket-owner-full-control` keep working; every other ACL write is refused by S3. The rule only tightens: `BucketOwnerPreferred`
and `ObjectWriter` let ACLs take effect and are not accepted, and the controls cannot be removed (removing them falls back
to `ObjectWriter`). The call needs confirmation and `s3:PutBucketOwnershipControls`.

## Objects

- `object.list` takes `prefix`, `delimiter`, `start_after`, `fetch_owner`, `encoding_type`, `optional_object_attributes`,
  `page_size` (1 to 1000), and `cursor`, and returns `contents`, `common_prefixes`, `key_count`, `next_cursor`, and
  `has_more`. `object.list-versions` takes `prefix`, `delimiter`, `encoding_type`, `page_size`, and `cursor`, and
  returns `versions` and `delete_markers`; its cursor holds both markers. A cursor belongs to the bucket and the
  arguments it came from.
- `object.head` and `object.get-attributes` return metadata, checksums, and user metadata without the content. A key
  that does not exist, and a delete marker, answer not-found. `object.head` returns the retain-until date but not a
  website redirect address.
- `object.copy` copies up to 5 GiB inside S3 and replaces what is at the destination. `copy_source` is `bucket/key`,
  percent-encoded, with an optional `?versionId=ID`. It must name a general purpose bucket: an access point, an
  Outposts, or any other ARN, and a name with a query other than `versionId`, are refused before any request, because
  their account could not be checked. The bound account is sent as the expected owner of the destination
  (`x-amz-expected-bucket-owner`) and of the source (`x-amz-source-expected-bucket-owner`), so S3 refuses a source in
  another account. S3 can report a failed copy with a success status; the tool turns that into an error and does not
  repeat the call. A KMS key must be an ARN of the bound account, as for `encryption.put`.
- `object.delete` deletes one object or, with `version_id`, one version for good; without it a bucket that keeps
  versions gets a delete marker. `object.delete-many` takes `delete.objects` (1 to 1000 keys, each with an optional
  `version_id`) and `delete.quiet`. The effect is the number of keys in the request; the answer lists `deleted` and
  `errors`, so a partial failure is a success status with a non-empty `errors`.
- `object.restore` starts the restore of an archived object (`restore_request.days` and
  `glacier_job_parameters.tier`). It costs money by tier and for the days the copy stays. Querying content with
  `SelectParameters` and output locations are not offered.
- `object-tagging.put` replaces all tags of an object; `object-tagging.get`, `.delete`, and `object-acl.get` read or
  remove as named. Keys, version IDs, user metadata, and tags are untrusted data.

S3 charges for every request, and for restores and transfer. A list or batch over many objects is billed per request.

Not offered on any object tool: ACL headers (`x-amz-acl`, `x-amz-grant-*`), customer-provided keys (SSE-C, also for the
copy source), `x-amz-website-redirect-location`, the request payer, MFA delete, the governance retention bypass, the Object
Lock settings of `object.copy`, and the KMS encryption context. Date members (`if_match_last_modified_time`, `last_modified_time`, `response_expires`, and the conditions on the copy source) are RFC 3339 date-times; the tool writes each in the form S3 expects. `PutObjectAcl` is never a tool.

## Reading Object Lock

- `object-lock.get` returns whether Object Lock is enabled and the default retention rule (`mode`, `days`, `years`, and
  `default_event_hold`). A bucket without Object Lock answers not-found (`ObjectLockConfigurationNotFoundError`, or
  `NoSuchObjectLockConfiguration`).
- `object-retention.get` and `object-legal-hold.get` take `key` (1 to 1024 bytes) and optionally `version_id`, and return
  `retention` (`mode`, `retain_until_date`, `event_hold`, `event_hold_duration`) or `legal_hold` (`status`, `ON` or `OFF`).
  A bucket without Object Lock answers not-found (`NoSuchObjectLockConfiguration`); an object without retention or a
  bucket that cannot hold Object Lock may answer `InvalidRequest`, which stays an invalid-request error and is not read as a
  missing object. Keys, version IDs, and dates are untrusted data.

The readers never write; the `RequestPayer` argument is not offered.

## Writing Object Lock

The confirmation of a call is the generic one; what it does is in the description of the tool.

- `object-lock.put` takes `object_lock_configuration`: `object_lock_enabled` (`Enabled`) and optionally a `rule` with
  `default_retention` (`mode`, `days` or `years`, `default_event_hold`). **Turning Object Lock on cannot be undone**: it
  stays on for the life of the bucket and needs versioning. A default retention protects every new object until its period ends.
  `token` is the token AWS Support issues to turn Object Lock on for a bucket created without it.
- `object-retention.put` takes `key`, optionally `version_id`, and `retention` (`mode`, `retain_until_date`, `event_hold`,
  `event_hold_duration`). The object cannot be deleted or overwritten until the retain-until date; the date can be
  extended but not moved earlier.
- `object-legal-hold.put` takes `key`, optionally `version_id`, and `legal_hold` (`status`, `ON` or `OFF`). A hold has no end date and can be set `OFF` at any time.
- Only the mode `GOVERNANCE` is accepted, in a retention and in a default retention; `COMPLIANCE`, any other spelling, and a
  missing mode are refused before any request. A call with neither `retention` nor `object_lock_configuration` is refused.
  There is no argument for `x-amz-bypass-governance-retention`: a governance retention can only be bypassed by a caller with
  `s3:BypassGovernanceRetention`, which no tool offers. `RequestPayer` is not offered either.

## Payment model

`request-payment.put` sets the payer of a bucket to `Requester` or `BucketOwner`; repeating it leaves the same result,
and it can be reverted at any time. With `Requester` the costs of transfer and requests move to whoever asks:
anonymous access is no longer possible, and requests of other accounts fail unless they send `x-amz-request-payer`.
The tool description names this effect, since the confirmation itself is generic.

## Inventory and analytics

`inventory.*` manages the inventory configurations of a bucket, `analytics.*` its storage class analytics
configurations. `get`, `put`, and `delete` take the configuration `id`; `put` also takes the whole configuration
(`inventory_configuration` or `analytics_configuration`, with the same `id`) and replaces the one with that ID. The lists
take `cursor` and return `next_cursor` and `has_more`; the cursor carries the continuation token of S3. Configuration IDs,
prefixes, and bucket names are untrusted data. The empty `sses3` element of an inventory encryption is an empty
structure and is not shown in a result. `put` and `delete` need confirmation, whose text is the generic one: the
description of the tool says that the call changes the named configuration of the named bucket and where its report goes,
and the arguments of the request carry the bucket, ID, destination, and region.

### Report destination

A report in the bucket of another account would be a standing data path out of the bound account. `inventory.put` and
`analytics.put` therefore accept only a destination in the bound account, judged in two steps. Before any request:

- The bucket must be a bucket ARN of the form `arn:aws:s3:::<name>`.
- The account ID of the destination (`account_id` of an inventory, `bucket_account_id` of an analytics export) must be
  set and be the bound account. A bucket ARN carries no account and a name alone does not exclude a bucket of another
  account, so a missing ID is refused and not filled in.
- An SSE-KMS key of an inventory (`ssekms.key_id`) must be the ARN of a key of the bound account in an allowed region.

Then the tool sends `HeadBucket` for the destination bucket with the bound account as expected owner and refuses the
call, without changing anything, on any failure (access denied, not found, a bucket of another owner, a timeout) or
a different owner. This needs `s3:ListBucket` on the destination. A destination in another region than the source
bucket is not refused: when the call region does not reach it, the other regions of the connection are tried. It is a
cross-region transfer that S3 charges for. An analytics configuration without a data export has no destination and is
not checked. The destination bucket's policy must allow S3 to write the reports; the tool does not change it.

Reports cost money: S3 charges for the listing it produces, for the storage the reports occupy, and for the requests that
write them. Deleting a configuration stops new reports and leaves the written ones.

## Reading the other configuration

`acl.get`, `website.get`, `logging.get`, `notification.get`, `replication.get`, `ownership.get`, `accelerate.get`, and
`request-payment.get` only read. `acl.get` returns the owner and the grants, each with the grantee (`type`, `id`,
`display_name`, `email_address`, `uri`) and the permission. The logging, notification, and replication configuration can
name buckets, topics, queues, functions, and accounts other than the bound one; they are returned unchanged as
untrusted data, and a reader neither follows a target nor fetches a URL
from it. That a bucket sends events to EventBridge is not shown, because the setting is an empty element that a result
does not carry. `ownership.get` shows the controls that `ownership.put` sets.

## Uploading and downloading objects

`object.upload` and `object.download` move the content of one object through a local file and nowhere else. Neither
takes the content as an argument, and neither returns it: the result holds metadata, `local_path`, `size`, and
`sha256`, the SHA-256 of the file as hex. Both take `bucket` and `key` (1 to 1024 bytes, untrusted text) and the
required `local_path`, an absolute path or one that starts with `~/`.

**Local files.** A tool is offered only by a connection that releases a directory for its direction in `files`:
`files.read` for `object.upload`, `files.write` for `object.download`. A path outside the released directories, with
`..`, through a symbolic link that leaves them, or to something that is no regular file is refused before any request, and
no message names the path. A download needs the directory of the file to exist. An existing file is replaced only
with confirmation: without it the call stops before any request and changes nothing. A failed or interrupted download
leaves no file and no partial file, and does not touch the file it would have replaced.

**Limit.** At most 100 MiB (104 857 600 bytes) per call, exactly that many allowed. An upload checks the size of the file
before it reads it. A download checks the `Content-Length` S3 states before it writes anything, refuses a larger
object, and cuts off a stream that runs past the announced size or ends before it. Larger objects are not reachable with
these tools, and the whole call must finish within the 60 second limit of an invoke.

**Integrity.** `object.upload` reads the file once to hash it, sends the SHA-256 as `x-amz-checksum-sha256`, which S3
verifies and answers `BadDigest` for when the content differs, and then streams the file. The checksum header is covered
by the signature; the payload itself is signed as `UNSIGNED-PAYLOAD` over HTTPS, since the stream is read once. A file that
changes while it is read is refused. `object.download` asks S3 for the stored checksum and, when S3 states a SHA-256
for the whole object, compares it with the content; a mismatch leaves no file. A checksum in another algorithm, one of a
multipart object, and the answer to a range or part request are not compared, but the number of bytes always is.

**Parameters.** `object.upload` takes `content_type`, `cache_control`, `content_disposition`, `content_encoding`,
`content_language`, `expires`, `metadata`, `storage_class`, `server_side_encryption` (`AES256` or `aws:kms`),
`ssekms_key_id`, `bucket_key_enabled`, `tagging`, `if_match`, and `if_none_match`. `ssekms_key_id` must be the ARN of a key
or alias of the bound account in an allowed region, like `kms_master_key_id` above. `if_none_match: *` writes only
when no object has the key, and a failed condition answers `PreconditionFailed`. Without a condition an upload replaces
an existing object (in a versioned bucket, with a new version), and repeating it writes again. `object.download` takes
`version_id`, `range`, `part_number`, `if_match`, `if_none_match`, `if_modified_since`, and `if_unmodified_since`. The
result of `object.download` carries the metadata of the object, including `metadata`, which is untrusted data, and its
Object Lock state.

**Not offered.** On both: ACL and grant headers, customer-provided keys (SSE-C), `WebsiteRedirectLocation`, `RequestPayer`
and `RequestCharged`, and the encryption context. Never an argument: the expected bucket owner, which is always the
bound account, the checksum headers (the tool sets SHA-256 itself), and a presigned URL, which no tool creates. On the
upload also: Object Lock settings (the object-lock tools set them, with governance retention only) and the append offset of directory buckets. On the
download also: the `response-*` overrides of response headers, which only matter to a client that serves the content on.

S3 charges for the requests and for data transferred out. Needs `s3:PutObject` and `s3:GetObject` (see
[Set up AWS](setup.md#s3)).

## Multipart uploads

Objects above 100 MiB are uploaded in parts: `multipart-upload.create` returns an `upload_id`, `upload-part` (from a local
file) or `upload-part-copy` (from an object in S3) sends each part, and `complete` joins them. `abort` deletes the parts
sent so far; `list` shows the uploads in progress of a bucket and `list-parts` the parts of one upload. All take `bucket`
and, except `list`, `key`; all but `create` and `list` take `upload_id`.

**Limits.** `part_number` runs from 1 to 100 and each part is at most 100 MiB (104 857 600 bytes), so one object reaches
about 10 GiB, the size of the largest local file. The limit is one constant in the code and can be raised later; S3 itself
allows 10 000 parts. No state is kept between calls: the limit holds because every part and the list of `complete` are
bound by the part number. S3 wants every part but the last to hold at least 5 MiB; a tool cannot see that at the call of
one part, so `complete` answers `EntityTooSmall` with a note on the minimum. Each call is bound by the 60 second limit of
an invoke, as for `object.upload`, so a slow link needs smaller parts.

**Parts from a file.** `upload-part` takes `local_path` as `object.upload` does (directories released in `files.read`, no
path in any message) and the optional `offset` (start byte, default 0) and `length` (1 to 104 857 600, default up to the
end of the file). The file may be larger than the part; without either, the whole file is the part and must fit the
limit. A range outside the file, or longer than 100 MiB, is refused before any request. The SHA-256 is computed over the
range only, sent as `x-amz-checksum-sha256`, and returned with `etag`, `size`, and `checksum_sha256`; send the parts of a
file with growing `offset`. Sending a part number again replaces that part, and the call is not repeated on a failure.

**Parts from S3.** `upload-part-copy` takes `copy_source` as `object.copy` does, with the same checks and the bound
account as expected owner of both buckets. `copy_source_range` is required, `bytes=FIRST-LAST` with at most 100 MiB.

**Complete.** `multipart_upload.parts` lists every part with `part_number`, `e_tag`, and `checksum_sha256`, in ascending
order (at most 100 parts). `create` starts the upload with the checksum algorithm SHA256 (the only value of
`checksum_algorithm`), because S3 holds the parts of an upload to one algorithm. S3 can report a failed completion with a
success status; the tool turns that into an error. `InvalidPart`, `InvalidPartOrder`, and `NoSuchUpload` are reported with
their codes. Metadata, `content_type`, and encryption of the object are set at `create`, with the parameters and the
exclusions of `object.upload` (no ACL, SSE-C, Object Lock, or redirect; a KMS key must be an ARN of the bound account).

**Cost.** The parts of an upload that is not completed or aborted stay in the bucket and are billed as storage until
`abort`. Add a lifecycle rule `AbortIncompleteMultipartUpload` to the bucket so that forgotten uploads are removed; the
tools do not set lifecycle rules. Needs `s3:PutObject`, `s3:AbortMultipartUpload`, `s3:ListMultipartUploadParts`, and
`s3:ListBucketMultipartUploads` (see [Set up AWS](setup.md#s3)).

## Never tools

| AWS operation | Why |
| --- | --- |
| `DeletePublicAccessBlock` | Removing the block is a loosening; the block is only kept or tightened. |
| `DeleteBucketOwnershipControls` | Removing the controls falls back to `ObjectWriter`, under which ACLs take effect; ownership is only set to `BucketOwnerEnforced`. |
| `PutBucketAcl`, `PutObjectAcl` | ACLs can open a bucket or object to the public and bypass the checks above. |
| `PutBucketWebsite` | A website endpoint publishes objects over plain HTTP. |
| `PutBucketLogging` | Access logs can be delivered to a bucket of another account, and nothing checks the target. |
| `PutBucketNotificationConfiguration` | Events can go to topics, queues, and functions of other accounts, and nothing checks the target. |
| `PutBucketReplication`, `DeleteBucketReplication` | Objects can be copied to a bucket of another account, and nothing checks the target. |

No tool writes an ACL, a grant, a website, logging, notifications, or replication, and none creates or returns a
presigned URL.
Setting lifecycle and CORS rules, intelligent tiering and metrics configurations, Object Lock in COMPLIANCE mode, bypassing a governance retention, and writing acceleration are not tools. Ownership is a tool only for `BucketOwnerEnforced`. Object content is a tool only for upload, download, and multipart upload through local files, up to 100 MiB per call.

## Limits

- No live test has been run against S3. The behaviour of `SlowDown`, request costs, and the exact error codes of the
  write operations is documented by AWS only and has not been verified; a code the table does not know is reported as
  an unknown code.
- The multipart tools were not run against S3 either. That S3 accepts parts with a SHA-256 checksum after `create` with
  `SHA256`, and `complete` with the checksum of every part, follows its documentation and is unverified.
- Everything S3 returns, including bucket names, tags, object keys, and version IDs, is untrusted data.
